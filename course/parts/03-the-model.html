Now we meet the model we will spend the rest of the course dissecting — and, just as importantly, the two false starts that led to it. The false starts are not filler: they are where the most general lessons live.

Attempt 1: plain sorting is counting

We first trained an ordinary transformer to sort a string of symbols from a 20-symbol alphabet into ascending order. It works. But when we looked inside, the attention was diffuse and uninformative — no crisp circuit. A simple experiment told us why. We varied the number of layers and measured accuracy:

LayersExact-sort accuracy
10.73
20.93
30.76
40.79

Accuracy peaks at two layers and falls with more. A comparison-based sorting network would only get better with depth. This signature — a two-stage optimum — is what you expect from counting sort: build a histogram of how many of each symbol you have, then read them out in order. Over a small alphabet, counting is easier than comparing, so gradient descent finds it, and there is nothing to "route" — hence the boring internals.

The lesson hiding here

A model solves the task the easiest way its data and architecture allow, not the way a textbook would. If we want to study routing circuits, we have to design a task where counting cannot win.

Attempt 2: sort key–value pairs (and an architecture wall)

So we changed the task. Each item is now a (key, value) pair. The model must output the pairs sorted by key, carrying each value along with its key. A histogram of keys tells you the sorted keys but says nothing about which value belongs to which key — so the model is forced to physically move each value from its input position to wherever its key lands. That is genuine routing.

We fed this to the same encoder architecture — and it could not learn it. Not with more layers, more width, more training, or easier variants. It reliably sorted the keys (by counting) and left the values at chance. We will unpack the deep reason in Lesson 5, but the one-line version is a preview of a theme:

Some tasks are unlearnable for one architecture and trivial for another. The architecture decides which algorithms are even reachable.

The model: a causal decoder

The fix was to change the architecture, not the task. We reframed sorting as autoregressive generation: the model reads the input pairs, then generates the sorted pairs one token at a time, left to right, with a causal mask. This trains easily and is the model we dissect. Concretely:

The exact setup

Input keys are distinct token ids 0–49; values are a disjoint set 50–69; then a separator SEP, and the model generates the sorted pairs, ending with EOS. The sequence is laid out interleaved:

k0 v0 k1 v1 … kₙ₋₁ vₙ₋₁  SEP  sk0 sv0 sk1 sv1 …  EOS
└──────── input pairs ────────┘      └── sorted output ──┘

Architecture: 2 layers, 2 heads per layer, d_model = 48, MLP width 96 — about 51,000 parameters. It reaches 99.9% exact-match generation at up to 30 pairs.

What "solving it" means, and how we test

Two evaluation modes recur throughout. Teacher forcing feeds the model the correct sequence and asks, at each position, whether its next-token prediction is right — handy for probing internal states at known positions. Autoregressive generation lets the model actually produce the output from scratch — the honest test of whether it "sorts."

A quirk to remember

The model never learned to emit EOS: that token was accidentally left out of the training loss, so it gets no signal to produce it and just keeps trying to sort. Our accuracy numbers therefore score the sorted pairs, not the end marker. We only discovered this while doing the failure-mode analysis in Lesson 8 — a small reminder that even "it works" hides details.

We now have a model that does real routing and is small enough to understand completely. Time to look inside. The most visual technique comes first: reading its attention.
