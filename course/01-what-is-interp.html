Foundations

What is interpretability?

Why open the black box, and the question we chose

A trained neural network is a big pile of numbers — weights — that somehow produce correct answers. Mechanistic interpretability is the project of turning that pile of numbers into an explanation: a description of the internal algorithm, in terms a human can follow, backed by evidence.

Definition

Mechanistic interpretability — reverse-engineering the specific computations a trained network performs, down to the role of individual components (attention heads, neurons, directions in activation space), and testing those roles with experiments rather than just telling a plausible story.

Why bother?

Two reasons, one practical and one scientific.

  • Trust and safety. If a model is going to make decisions that matter, "it usually gets the right answer" is not enough. We want to know how it decides, so we can predict when it will fail, catch deception, and fix it at the mechanism instead of by trial and error.
  • Science. Networks trained by gradient descent discover solutions no human designed. Some are elegant, some are bizarre. Understanding them is genuinely new knowledge about what computation looks like when it is found rather than written.

What counts as an explanation

The trap in interpretability is the just-so story: you look at a picture, say "this head looks like it tracks subjects," and move on. That might be true. It might also be pattern-matching on noise. The discipline of this field is that a claim about a mechanism has to make a testable prediction, and you have to run the test.

The core move

Observation suggests a mechanism; intervention confirms it. If you think a head "copies the value," then deleting that head should break value-copying and nothing else — so delete it and measure. Throughout this course, every observation is followed by an experiment that could have proven it wrong.

The question we chose

Sorting is a beautiful test case because computer science already knows dozens of sorting algorithms, each with a distinctive structure. So we can ask a sharp question:

If you train a transformer to sort, does it discover a recognizable sorting algorithm inside — and if so, which one, and can we prove it?

That question turned out to have a surprising, multi-part answer, and chasing it down is the spine of this course. Here is the shape of the journey, so you know where we are going:

  1. Plain sorting is "cheating." Over a small set of symbols, the easiest way to sort is to count how many of each symbol you have and emit them in order — no comparisons, no moving things around. The model finds this, and its internals look boring precisely because counting is so simple.
  2. Forcing real work. To make the model actually route information, we change the task: sort (key, value) pairs by key, and carry each value along with its key. Now a value has to physically travel from its input slot to wherever its key ends up — counting can't fake that.
  3. An architecture wall. The standard encoder we started with cannot learn the pair task at all. Understanding why teaches us something deep about what different architectures can and cannot represent.
  4. The crack. A causal decoder learns it easily, and inside we find a crisp, understandable circuit. The rest of the course is taking that circuit apart.
Honesty note

Real research is not a clean march to the right answer. We made wrong turns and overclaimed things that later analysis corrected. This course keeps those in — including a whole lesson on what we got wrong — because knowing how a conclusion can be wrong is part of learning to do this well.

To reverse-engineer the model we first have to understand how it is built. That is the next lesson: a transformer, from tokens up.
